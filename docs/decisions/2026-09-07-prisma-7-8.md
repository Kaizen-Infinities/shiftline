# Decision: stay on Prisma 6 through Phase 1; plan the Prisma 8 move as its own package

Date: 2026-09-07 · Status: accepted · Owner: platform

## Facts (checked against the npm registry on the date above)

|             | Version                        | Notes                                                                                                                                        |
| ----------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Installed   | prisma / @prisma/client 6.19.3 | `prisma-client-js` generator, Rust query engine, `prisma.config.ts`                                                                          |
| Latest GA   | 7.10.0                         | ESM-first `prisma-client` generator, driver adapters (`@prisma/adapter-pg`) required, no runtime `Prisma.dmmf`, `prisma.config.ts` mandatory |
| Pre-release | 8.0.0-rc.13, 8.1.0-dev         | New CLI toolchain (`@prisma/orm-toolchain`); `@prisma/config` no longer a direct dependency                                                  |

The open advisory GHSA-ggr8-5vv4-36mx (deepmerge-ts < 8, stack exhaustion on recursive
objects) reaches us only through `prisma → @prisma/config → deepmerge-ts 7.1.5`, i.e. the CLI
loading `prisma.config.ts` at migrate time. **Prisma 7.10.0 still pins deepmerge-ts 7.1.5**, so
upgrading to 7 does not close it; the 8 release candidates drop the `@prisma/config` dependency
chain. The allowlist entry stays, with its 2026-12-31 expiry, and its note now says "verify on 8.0
GA" rather than "fixed in 8.1".

## What the upgrade touches in Shiftline

- `lib/prisma.ts`: `TENANT_MODELS` is derived from `Prisma.dmmf` at runtime; 7+ removes the
  runtime DMMF. Replace with a generated list (a build step over the schema) or the new
  `runtimeDataModel`.
- `scripts/gen-rls-migration.ts`, `scripts/gen-audit-migration.ts`, `test/helpers/db.ts`,
  `test/integration/leak.spec.ts`: same DMMF dependency (build-time only; can use `@prisma/internals`
  `getDMMF`).
- The `$extends` tenant extension and the `$transaction` proxy: re-verify typings and the
  `createManyAndReturn`/`updateManyAndReturn` paths on the new client.
- Connection: driver adapter `@prisma/adapter-pg` with `pg` pool; `sessionSettings()` still runs as
  the first statement of each transaction, so RLS is unaffected, but the pool becomes ours to size.
- Generated client location and import paths (`prisma-client` emits to a folder we choose; ESM
  output must work with `tsx` in dev and the Docker build).
- CI migration gate and the audit-gate allowlist.

Estimated effort: 3–4 engineer-days including a full regression (API suite, leak and RLS suites,
browser suite, restore drill), most of it in the DMMF replacement and adapter wiring.

## Decision

Phase 1 is finance-heavy and every package adds models to the tenancy extension; changing the ORM
runtime underneath that work would put the tenancy guarantees at risk for no functional gain.
Prisma 6.19 is current within its major, receives fixes, and the only open advisory is
build-time-only and allowlisted with an expiry.

- Stay on Prisma 6.19.x for Phase 1. Bump patch releases as they land.
- Schedule "Prisma 8 migration" as a dedicated package right after Gate 1, or earlier if Prisma 6
  reaches end of support or a runtime advisory appears. Preconditions: 8.0 GA published,
  `@prisma/adapter-pg` GA, this document's checklist.
- Keep the data model changes that make the move easier: uuid primary keys everywhere (done with
  the tenant-scoped codes work), no reliance on client-generated uuids in migrations, no batch
  `$transaction([...])`.

## Re-evaluate when

Prisma 8.0 GA ships, the deepmerge-ts allowlist entry approaches expiry (2026-12-31), or Prisma
announces the 6.x end-of-support date.
