# P2-15 — HR shared pieces: employee picker, business place, leave and fines polish

## Shipped

- `GET /api/employees/search?q=` (`apps/api/src/modules/employee/{employee.routes,employee.
controller,employee.service}.ts`) behind a new `employees.search` key — id, code, name,
  department, business place; active employees only, capped at 20 rows, ordered by name.
  `employees.search` was added to the existing `employees` module in `packages/shared/src/
permissions.ts` (already in the `core` feature) and granted, in `provisioning.service.ts`, to
  every role that already holds `leave.view`, `fines.view` or `payroll.view` — in practice every
  seeded role (OWNER gets it through the "everything" flatMap already).
- Web `EmployeePicker` (`apps/web/src/components/common/EmployeePicker.tsx`): a debounced
  typeahead over that endpoint — used by `LeaveHrPage`'s request form and `FinesPage`'s create
  form in place of a raw "Employee ID" text box. Both forms now refuse to submit client-side
  until a match is actually picked (`toast.error("Pick an employee first")`), since the picker
  itself only applies native `required` to its own text field, not to the resolved id.
- `Employee.businessPlaceId` (nullable `BigInt`, relation to `BusinessPlace`; migration
  `20260914150000_hr_shared`): additive column plus index and FK, with a data step that defaults
  every employee's business place to the company's one where a tenant has exactly one (every
  demo/seeded tenant, and most tenants day one) — a multi-branch tenant gets no default and
  assigns each employee explicitly. Exposed on `employee.service.ts` create/update (validated
  against `BusinessPlace` the same way `asset.service.ts` validates the same column elsewhere —
  an unknown id is refused with 400) and on `EmployeeForm.tsx` as a plain id field, matching the
  existing convention on `RegistersPage.tsx`'s own business-place filter (there is no
  business-place _listing_ endpoint anywhere in the app yet to back a dropdown).
- `registers.service.ts`'s `businessPlaceId` filter now actually filters (P2-03 shipped it as
  validate-only): directly on `Employee` for the muster roll and wages registers, through the
  employee relation for fines, deductions and advances, and by the resolved employee-id set for
  the overtime register, whose source (`AttendanceRecord`) still carries no business-place link
  of its own.
- Leave calendar: `/hr/leave`'s calendar tab renders a month grid (employees down, days of the
  month across, the leave type code in each covered day) built client-side
  (`buildCalendarGrid` in `LeaveHrPage.tsx`) from the existing `GET /api/leave/calendar` response
  — no backend change, since folding a month's approved requests into a grid is cheap either way.
- `LabourEntitlementsPage.tsx`'s "Leave" tab gained a leave-types table with an `allowNegative`
  toggle per type, wired through a new `labourService.saveLeaveType()`. This also fixes a real
  bug found along the way: `POST /api/labour/leave-types`' zod schema never had an
  `allowNegative` field, so the API silently dropped it even though `labour.service.ts`'s
  `upsertLeaveType` already accepted and stored it — the P2-09 hand-off's "the API already
  accepts it" was only half true. Added to the route's schema.
- `PATCH /api/fines/:id` (`fines.service.ts#update`): amount, cause, date, wage period on a
  still-`PENDING` item; refused once a show-cause is recorded (`SHOW_CAUSE_RECORDED`, 409) or
  once approved (`NOT_PENDING`, 409, same code the other actions already use for a non-pending
  item). An "Edit" action on `FinesPage.tsx`'s dialog, next to Show-cause.
- Fines notifications: the employee's linked user (if any, via `prisma.user.findUnique({ where:
{ employeeId } })`) is notified through the existing `notify` helper on `show-cause` and on
  `approve` — category `fines`, level `WARNING` for a fine and `INFO` for a deduction, the same
  shape `leave.service.ts#notifyDecision` already uses for leave outcomes. Never throws into the
  caller's flow, same as every other `notify` call.
- `apps/api/test/integration/hr-shared.spec.ts` (7 tests): search finds by name and by code and
  caps at 20 rows, refused for a role with none of the three permissions (a fresh `Role` row with
  no `RolePermission` grants — every seeded role now holds `employees.search`, so the refusal
  test could not reuse one), cross-tenant isolation; employee create/update round-trips
  `businessPlaceId` including clearing it back to null, an unknown place refused on both create
  and update; the wages register's business-place filter excludes an employee at a different
  business place and includes them again unfiltered; a fine's edit succeeds while `PENDING`, is
  refused once show-cause is recorded, is refused once approved, and both the show-cause and the
  approval leave a `fines`-category notification for the linked employee; a deduction (which
  never needs a show-cause to approve) can still be edited while `PENDING`.

## Decisions worth knowing

- **`employees.search` went to every seeded role, not a hand-picked subset.** The task said
  "every role that has `leave.view`, `fines.view` or `payroll.view`" — checking `provisioning.
service.ts` against that criterion, that is in fact all six seeded roles (OWNER, ACCOUNTS,
  STORES, PRODUCTION, SALES_EXEC, AUDITOR all hold at least one of the three already for
  self-service leave or approval). The permission-refusal test therefore has to construct a
  bespoke role with zero grants rather than reuse a named seeded one.
- **The business-place id on the employee form is a plain text field, not a dropdown**, because
  no `BusinessPlace` listing endpoint or picker component exists anywhere in the app yet —
  `RegistersPage.tsx`'s own business-place filter is the same raw-id pattern. Building a proper
  picker was out of scope; the id is validated server-side either way.
- **The overtime register filters by an employee-id set, not a join**, because `AttendanceRecord`
  has no `businessPlaceId` of its own (P2-03's original gap, only half-closed here — see below).
  The muster roll and wages registers filter `Employee` directly (or through `PayrollResult.
employee`), which is simpler and was the more common case to get right.
- **The employee search endpoint returns id/code/name/department/business-place only** — no
  payroll, salary or identity fields — deliberately narrower than `GET /employees/:id`, matching
  why it sits behind a lighter key than `employees.view`.

## Half-done / known gaps

- `AttendanceRecord` still carries no `businessPlaceId`. The muster roll and overtime registers
  filter through the employee-id set a business place resolves to rather than a real column on
  attendance, which is correct today (an employee has one business place) but would need an
  actual `AttendanceRecord.businessPlaceId` if attendance is ever recorded per-location for an
  employee who moves between places.
- **No `BusinessPlace` picker component or listing endpoint** exists yet — the employee form and
  the registers filter both take a raw id. A proper dropdown is a natural next step once
  something else needs one too.
- **The leave request list still shows a raw employee id**, not a name — `EmployeePicker` closed
  the _input_ gap on both HR forms, but neither `LeaveHrPage`'s request table nor the calendar's
  "who is off" list was changed to resolve `employeeId` to a name outside of what the calendar
  endpoint already returns; only the calendar grid (built from rows that already carry
  `employeeName`) shows names.
- The migration's default-business-place data step only fires for a tenant with exactly one
  `BusinessPlace` at migration time; a tenant that adds a second branch later never gets employees
  retroactively assigned — expected, since the task asked for a same-migration default only where
  unambiguous.

## Blocked on the owner

Nothing — no external account or credential is needed for this package.

## Changelog

- Leave and fines forms now search for an employee by name instead of asking for a raw id, the
  leave calendar shows a month at a glance, leave-without-pay can be toggled per leave type, a
  pending fine or deduction can be corrected before approval, and the employee is notified when a
  show-cause is recorded or a fine is approved.
