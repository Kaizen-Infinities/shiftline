# P2T-04 bug fixes — the six defects characterised, now fixed

## Shipped

All six real bugs P2T-04's characterisation work found (`docs/handoff/2026-09-13-P2T-04-characterisation.md`,
`docs/handoff/2026-09-13-phase-2-t-complete.md`) are fixed, on their own right after that
package, at the owner's explicit request ("fix all found bugs"):

1. **Permission-key mismatch (PRODUCTION role).** `ROLE_DEFS()`'s `PRODUCTION` entry in
   `provisioning.service.ts` now spells its module keys exactly as `PERMISSION_REGISTRY` does:
   `production-orders` → `production_orders`, `weekly-programs` → `weekly_programs`,
   `daily-plans` → `daily-machine-planning`, `hourly-production` → `hourly_productions`,
   `production-wastage` → `production-wastages`, and `oee` → `oee-dashboard` (a sixth mismatch
   in the same entry, found while fixing the other five). `demo.production` now gets 200 instead
   of 403 on production orders, hourly production and the OEE dashboard.
2. **OEE snapshot upsert used the wrong compound-unique key.** `oeeService.recalculateAndSaveSnapshot()`
   now upserts on `companyId_machineId_productionDate_shiftId` (the schema's real generated key,
   with `companyId` from `requireTenantId()`), not `machineId_productionDate_shiftId`. Every call
   through the normal flow (hourly production → OEE recalculation) now actually writes a row.
3. **goods-dispatch lost tenant context inside its own transaction.**
   `StockAdjustmentService.getNextAdjustmentNumber()` now takes an optional `Db` client (default
   `prisma`), and `goods-dispatch.service.ts`'s `storeReceive()` passes its own `tx`. A tenant's
   second (and every later) store-receipt of the year now gets the next sequence number instead
   of 409ing on a collision with sequence one.
4. **production-order's Zod defaults fired on absent keys.** `productionOrderBodyShape` no longer
   calls `.default(...)` on `producedQty`, `rejectedQty`, `scrapQty`, `priority`, `orderType`,
   `status` or `rawMaterials` — just `.optional()`. `create()` already had its own fallbacks
   (`?? "MEDIUM"`, hardcoded zeros, a ternary for `status`) so its behaviour is unchanged; a bare
   `PUT { status }` no longer wipes `draftRawMaterials`, and a locked order's PUT correctly
   allows the transitions `VALID_TRANSITIONS` permits instead of being locked out forever.
5. **start-production's idempotency guard never matched.** The legacy (no `dailyPlanId`) branch
   in `startProduction()` now checks `sourceDocId: productionOrderId` — what the create call two
   lines below it actually writes (`sourceDocId: dailyPlanId ?? productionOrderId`) — instead of
   `sourceDocId: null`, which the insert never sets. Calling `start-production` twice with no
   daily plan no longer double-issues materials.
6. **grn-invoice had no permission gate.** `grn-invoice.routes.ts` now calls `requirePermission`
   with `invoice.view`/`.create`/`.edit`/`.delete` alongside the existing `requireFeature("purchase")`,
   matching the registered `invoice.*` keys and what AUDITOR is deliberately limited to
   (`invoice.view` only). While touching this file, its dead duplicate `PUT /:id` registration
   (unreachable — Express already matched the first one) was removed. Enforcing the gate for
   real surfaced an adjacent gap in the same seed: ACCOUNTS — described as "Books, invoices,
   payments, reports" — never actually held the `invoice` module in `ROLE_DEFS()`, which would
   have locked it out of GRN invoices along with AUDITOR. Added `"invoice"` to ACCOUNTS'
   `keysFor()` list so the role meant to do this work still can. (ACCOUNTS separately lists
   `"purchase-orders"`, which does not match the registry's `"purchaseOrders"` — the same class
   of bug as #1 above, in a different role and module. Left alone: unrelated to this file, and
   not something this fix depends on.)

## Found in passing, not fixed here

Running the suite close to 18:30 UTC surfaced a live, real bug unrelated to anything in this
note: `inventory.service.ts`'s `getEodStock()` builds "today's" IST-day start as
`new Date(Date.UTC(nowParts.year, nowParts.month, nowParts.day))` — UTC midnight of the IST
calendar day's own date, not the true UTC instant of IST midnight (`18:30 UTC` the previous day,
since IST is UTC+5:30). For roughly the first 5.5 hours of every IST day (18:30–00:00 UTC), any
raw-material or finished-goods transaction that happens in that window is excluded from "today's"
net-change calculation, so the EOD "today" view's `startQty` comes out wrong (equal to the live
balance, as if nothing had moved yet). `inventory.spec.ts`'s first two tests fail exactly in this
window and pass outside it — not flaky in the usual sense, but wrong on a predictable clock. Not
fixed here: it is a different module than anything P2T-04 characterised or this pass touched, and
deserves its own change rather than a drive-by fix.

## Changelog

Production/Supervisor users can now see their own production orders, hourly production logs and
OEE dashboard. A second finished-goods receipt in the same year no longer fails. Editing a
production order's status no longer clears its material plan, and a production order in progress
can now be moved through its remaining stages. Starting production twice by mistake no longer
issues raw materials twice. Only Owner and Accounts can create or cancel a goods-receipt invoice;
Auditor can still view it.
