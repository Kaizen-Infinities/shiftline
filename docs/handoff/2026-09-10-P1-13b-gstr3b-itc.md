# P1-13b — GSTR-3B and the input tax credit ledger

## Shipped

- `itc.service.ts`: fills the `ItcEntry` table whose schema landed in `a27656d` (that commit said
  "service, GSTR-3B builder and routes follow in the next commit"; the frontend merge went in
  first, so the table sat unused until now). One row per inward document carrying GST — GRN
  invoices, expenses, petty cash — keyed `[companyId, docType, docId]`, upserted on every build
  and never deleted. Each row carries the split, the source (`RCM`, `IMPORT_GOODS` /
  `IMPORT_SERVICES` from an OVERSEAS supplier, else `OTHER`) and an eligibility call:
  `INELIGIBLE` rule `17(5)` for a blocked HSN (`BLOCKED_HSN_PREFIXES`) or an expense flagged
  `itcEligible: false`, `VOID` rule `CANCELLED` for a cancelled document, else `ELIGIBLE`.
- Rule 37 in the same service: a bill unpaid 180 days after its date, measured at the end of the
  period being built, goes to `REVERSED` with `reversedPeriod`; once paid it goes to `RECLAIMED`
  with `reclaimedPeriod`. Payment is the sum of `GrnInvoicePayment` rows on or before the period
  end against `netAmount`. Those two columns — not the availment month — are what tables 4B(2)
  and 4D(1) read, so a reversal lands in the month it actually falls due.
- `gstr3b.service.ts` + `gstr3b.types.ts`: tables 3.1(a–e), 3.1.1, 3.2 by place of supply,
  4 (A by source, B reversed, C net, D reclaimed/ineligible), 5 and 6.1. Outward figures come
  from the same documents GSTR-1 reads, net of credit notes; the credit side comes only from the
  ledger, and the return carries the ledger rows so an accountant can trace any figure to a
  document and the rule that classified it. Set-off in 6.1 follows sections 49A/49B (IGST credit
  first, then CGST and SGST against their own head and the balance against IGST); reverse-charge
  tax is never set off against credit.
- Routes next to GSTR-1: `GET /api/gst-returns/gstr3b`, `POST .../gstr3b/register`,
  `POST .../gstr3b/filed`, `GET /api/gst-returns/itc`, `PATCH /api/gst-returns/itc/:id`, behind
  the existing `gst-returns.{view,prepare,file}` permissions. Filing goes through
  `filingApprovalService.assertSubmittable` as `GSTR3B` with the hash of the tables. Paths added
  to `packages/shared/src/api-paths.ts`; no new permission keys were needed.
- `gstr3b.spec.ts`, 4 tests: a golden month (three domestic sales, an export, a credit note, three
  GRNs including an import, a reverse-charge expense, a blocked-credit expense, a petty cash bill
  and a purchase return) asserted table by table with hand-computed values, including the whole
  set-off and the ₹5,256 cash payable; rule 37 reversing in December and reclaiming in January; a
  hand classification surviving a rebuild and a cancelled GRN going VOID; permission refusal, a
  bad period and the filing gate.

## Half-done / known gaps

- Table 4B(1) is zero: rules 38/42/43 proportional reversal needs an exempt-turnover ratio the
  books do not carry. The build emits a warning whenever any credit is available, so the figure
  is never silently wrong — but a company with exempt turnover has to compute it by hand today.
- Table 3.1.1 (supplies under section 9(5) through an e-commerce operator) is zero and labelled;
  nothing in the schema models an ECO supply yet.
- Table 3.1(e) non-GST outward supplies is zero for the same reason.
- 4A(1)/4A(2) recognise an import only from an OVERSEAS supplier on the document. Customs duty
  and IGST on imports are P1-17; until then an import GRN is taxed as an inter-state supply,
  which is the same treatment P1-08b left in place.
- `BLOCKED_HSN_PREFIXES` is the common section 17(5) set, not the whole section. The per-document
  flag and the manual reclassification are the real control; the list only catches the obvious.
- Petty cash carries one GST figure with no supply type, so its split is inferred from the vendor
  GSTIN's state against the company's. That is right for the ordinary case and wrong for a
  bill-to-ship-to; the field app does not raise those.
- There is no GSTR-3B portal JSON and no web screen — both belong to P1-13c/d by the brief.

Unchanged, and none of it blocked this package: GSP sandbox credentials (e-invoice, e-way bill,
IMS and returns APIs); branch protection and the named human approver for filing PRs — this is
one; a pentest vendor; the Anthropic API key decision for cheque OCR; the terms-of-service text.

One new question for an accountant, whenever the validation month happens: this build puts
section 17(5) blocked credit in table 4D(2) and keeps it out of 4A(5) entirely, so 4C is what is
actually claimable. Some filers instead route 17(5) through 4A(5) and reverse it in 4B(1). Both
land on the same net credit; they differ in what the portal's tables show. Confirm which the
company's auditor expects before the first live filing.
