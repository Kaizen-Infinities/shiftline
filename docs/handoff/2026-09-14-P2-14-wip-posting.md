# P2-14 — Post work in progress to the books

## Shipped

- **A `WIP` ledger** (`Work in Progress`, current asset) added to `DEFAULT_SEED_LEDGERS`
  (`apps/api/src/modules/accounts/accounts.service.ts`) — every existing tenant gets it the next
  time `ensureSystemLedgersExist()` runs (it already runs from `provisionTenant()`, and from
  `postClosingStock` itself), and every new tenant gets it on day one. No backfill migration
  needed.
- **`CostingSetting`** (`apps/api/prisma/schema.prisma`, migration `20260914140000_wip_posting`):
  one row per tenant, `wipLedgerCode` (default `WIP`). `GET/PUT /api/costing/settings`
  (`costing.service.ts` `getSettings`/`updateSettings`, `costing.routes.ts`) behind the existing
  `costing.view`/`costing.manage` permissions — no new permission keys needed. A tenant that
  never visits the setting reads the default without a row ever existing; `PUT` checks the code
  against the ledger table and refuses an unknown one with `UNKNOWN_LEDGER`.
- **`postClosingStock` posts WIP**, in the same voucher as the stock movement it already posted:
  `wipMovement = wipService.total() − (WIP ledger's booked balance as of the day before the
period, from POSTED vouchers)`. A rise moves Dr WIP / Cr Closing Stock; a fall reverses it. Two
  identities hold after every posting — checked directly in the tests rather than by trusting the
  arithmetic that produces them:
  - the WIP ledger's balance equals `wipService.total()` at the period date;
  - the closing-stock ledger's (`STOCK-001`) balance equals the valuation total minus WIP.

  Because the movement is a delta from what the WIP ledger already books, re-posting the same
  period is a no-op — the existing "already posted" guard now checks either leg, not just the
  raw-material movement, so a period where only WIP changed still posts. Cancelling the
  closing-stock voucher reverses the WIP leg with it for free, since it is a line in the same
  voucher and the existing cancellation path reverses every line.

- **Balance sheet**: the blended `STOCK-001` ("Closing Stock") ledger is split into "Raw Material
  Stock" and "Finished Goods Stock" for display, computed from the valuation ledger's own item
  types in the same ratio (the two add back to exactly what `STOCK-001` books, so no total
  changes) — `accounts.service.ts` `getBalanceSheet`. WIP already has its own real ledger and
  needs no splitting; it shows up next to the split automatically since it carries the same
  `STOCK_IN_HAND` schedule group (`ledgerGroups.ts`).
- **`GET /api/costing/valuation/:periodKey/closing-stock-status`** (read-only, `costing.view`):
  whether a period is posted, and whether the posted WIP figure still matches the live one — the
  costing screen's WIP card uses it to say so, without ever posting anything itself.
- **Web**: the costing screen's WIP card (`apps/web/src/modules/accounts/pages/CostingPage.tsx`)
  shows posted/not-posted for the selected period, and a ledger picker behind `costing.manage` to
  change `wipLedgerCode`, backed by `accountService.fetchLedgers({ type: "ASSET" })`. The existing
  route and sidebar entry cover it — nothing new for `e2e/smoke.spec.ts`, same as P2-04.
- Migration `20260914140000_wip_posting`: `costing_settings` (RLS + audit trigger, since which
  ledger WIP posts to is a books decision worth arguing about the same way any other posting
  setting is). `CostingSetting` added to `audited-models.ts` and to `leak.spec.ts`'s
  `MODELS_WITHOUT_SEED_ROWS`.
- Spec `docs/specs/P2-14-wip-posting.md`; tests `apps/api/test/integration/wip-posting.spec.ts`
  (9 tests, on a dedicated tenant rather than the shared demo one — WIP starts at zero and
  nothing here can be disturbed by another spec file's production orders).

## Decisions worth knowing

- **WIP posts against the blended stock ledger, not a split raw-material one.** The brief named
  "Dr WIP / Cr Raw Material Stock"; this codebase has no separate raw-material ledger — `STOCK-001`
  already blends raw material and finished goods, and always has (P1-19). Crediting `STOCK-001`
  for the WIP carve-out is the same instruction applied to the ledger that actually exists, and it
  produces exactly the identity the brief asked for: `STOCK-001` reads as valuation minus WIP. A
  real raw-material ledger, separate from finished goods, is a bigger change than this package's
  brief covers (see Out of scope).
- **The WIP "movement" is a delta from the WIP ledger's own booked balance, not from
  `wipService.total()` at the previous period's date.** `wipService` has no notion of "as of a
  date" — it reads current DB state (open orders, unreversed issues) — so "what changed since
  last period" has to be read off the books themselves, the same way the raw-material movement
  already was. This is also what makes cancel-and-repost, and skipping a period, come out right
  without extra bookkeeping.
- **The balance sheet's raw-material/finished-goods split is computed, not booked.** Actually
  splitting `STOCK-001` into two real ledgers would mean re-plumbing every place that posts to it
  (GRNs, adjustments, the closing-stock voucher itself) — P1-19's blended-ledger decision, not
  this package's to unwind. The display split is exact (it is built from the same valuation rows
  the ledger's own balance is trued up against) and costs nothing to remove later if a real split
  is ever built.
- **A test tenant, not the demo one.** Every other P2-04/costing spec shares the demo tenant and
  its WIP ledger would start at whatever other spec files left it at, on whichever database
  worker vitest happens to schedule the file onto — this package's identities (WIP ledger ==
  `wipService.total()`) need a clean zero to check against.

## Half-done / known gaps

- No real raw-material/finished-goods ledger split — see above. Anyone who wants to post
  differently against raw material and finished goods stock still cannot.
- The costing screen's period selector is shared with the "cost centres" tab and only rendered
  there; the "stock" tab's Post button and the new posted/not-posted card use whatever period
  that selector is on. A dedicated period picker for the stock tab is a small follow-up, not
  touched here to keep this package additive.
