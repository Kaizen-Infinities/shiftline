# P1-22 — SMS and one-time passwords

## Shipped

- `sms.calc.ts`, the rules a telecom operator enforces silently, apart from the database so each
  can be tested against the rule rather than the code:
  - **Number normalisation**: every form a ten-digit Indian mobile is typed in (`+91`, `0091`,
    a leading `0`, spaces and dashes), and `null` for anything that is not one.
  - **Segment counting** on GSM 03.38: 160 characters in one part, 153 once it splits, 70 and 67
    in UCS-2, with the extended characters (`{}[]~^|\€`) counted twice as the operator counts
    them.
  - **Template rendering** that refuses a missing or blank variable, and refuses a value carrying
    a link or a line break.
- `SmsProvider` with a fixture adapter that refuses what a real gateway refuses: a transactional
  message with no DLT template id, a send with no registered sender id, a promotional message to
  a number on the do-not-disturb registry.
- Per-tenant account settings: provider, DLT principal entity id, six-letter sender id, the auth
  key **encrypted at rest and never returned**, and a daily cap the tenant sets on itself.
- **Templates as rows** — code, DLT template id, category, body and its variables — seeded with
  `OTP`, `PAYMENT_LINK` and `PAYMENT_RECEIVED` on first use, each without a DLT id because that
  is the tenant's to register.
- A **message log** of every send, with what the gateway said about the ones it refused.
- **One-time passwords**: six digits, stored only as a bcrypt hash, ten-minute expiry, five
  attempts, three codes per number per purpose per fifteen minutes, and one live code at a time.
  The code is in no response and no log — the message row carries it masked to its last two
  digits.
- Routes under `/api/sms`, migration `20260913070000_sms_otp` with RLS and an audit trigger on
  the templates, web `/settings/sms`, in `e2e/smoke.spec.ts`. 14 unit tests and 10 integration
  tests.

## Decisions worth knowing

- **No live MSG91 adapter, deliberately**, for the same reason as P1-21's gateway: no account was
  supplied, so there is nothing to certify against. The registry returns an adapter that refuses
  loudly and a test holds it to that.
- **A template is a row, not a string in the code.** The body has to match the DLT registration
  character for character, and the registration is per tenant. A template in code would be a
  message that is registered for nobody.
- **A variable cannot carry a link or a newline.** That is exactly how a registered template gets
  used to send something it was never registered for, and it is why operators drop messages. The
  refusal costs a caller nothing and closes the hole.
- **The code is hashed with bcrypt, not SHA-256.** Six digits is a million possibilities: a fast
  hash in a leaked database is no protection at all, and this is verified once per attempt, so
  the cost does not matter.
- **The attempt counter does not move for an expired or spent challenge.** Counting those would
  let somebody burn a challenge's attempts without ever guessing at the code.
- **The account row is not audited**, though the templates are. Audit rows are never deleted and
  the account holds an encrypted credential; auditing it would keep old ciphertext forever.
- **The OTP endpoints sit behind a session.** Issuing a code to an unauthenticated caller is what
  an OTP _login_ needs, and that is an auth change — which by this repo's own rule needs the
  named human approver. The challenge service is built and tested so that change is small.

## Half-done / known gaps

- **The live adapter** (above), and with it the delivery-receipt webhook: `DELIVERED` is in the
  status set and nothing ever sets it.
- **OTP login is not wired into authentication.** See above; deliberate.
- **Nothing sends anything by itself.** No payment link, invoice or reminder goes out over SMS
  yet — the templates for them exist and the send endpoint works, but no flow calls it. Wiring
  `PAYMENT_LINK` into P1-21's link creation is the obvious first one.
- **No queue.** A send is synchronous inside the request; a slow gateway slows the caller. It
  belongs on pg-boss with a retry, and is not there.
- **No per-user rate limit on requesting codes**, only per number and purpose. A caller with a
  session can walk a list of numbers.
- The daily cap counts messages, not segments, so a long message costs the same against the cap
  as a short one though it costs more to send.
- Templates cannot be deleted from the screen, only deactivated.

## Blocked on you

- An **MSG91 account** (or another provider) with an auth key, and the tenant's **DLT
  registration**: the principal entity id, the sender id, and a registered template id for each
  of the three seeded templates. Without the DLT ids nothing is delivered, whatever the code
  does.
