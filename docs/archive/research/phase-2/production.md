# Production Management — Domain Research

## 1. Inventory

### Prisma models (apps/api/prisma/schema.prisma)

- `Machine` (L1145) — tonnage/technology master. Fields: `technologyType` (enum: INJECTION_MOULDING, EXTRUSION, BLOW_MOULDING, ROTATIONAL_MOULDING, THERMOFORMING, COMPRESSION_MOULDING, PRINTING, GRANULATION, MIXING, RECYCLING), `machineType` (PRODUCTION/UTILITY), `targetTemperature`, `targetLoadPercent`, `cycleTime` (single static Decimal, not per-product/per-mould), `machineStatus` (enum), `operatorId` (loose string, not FK to Employee). No mould/die link, no capacity (tonnage) field, no maintenance fields.
- `MachineOperationAssignment` + `MachineAssignmentOperator` (L1462) — weekly machine↔shift↔incharge↔operators roster.
- `WeeklyMachineProgram` (L1533) — week/day/machine/shift/product/qty plan tied to a `ProductionOrder`.
- `DailyProductionPlan` (L1612) — day/machine/shift plan, `carryForwardFromPlanId` self-relation, `currentProductionStep`/`currentStepIndex` (workflow state machine).
- `HourlyProduction` (L1575) — per-hour qty/reject/scrap/downtime; `downtimeReason`, `rejectReason`, `scrapReason` are **free-text VarChar(100)**, not FKs to a reason master.
- `ProductionOrder` (L1366) — full shop order incl. `producedQty/rejectedQty/scrapQty`, `requiredRawMaterialQty`, `draftRawMaterials` (Json), step-workflow fields, links to BOM/routing (both just string ids, no `Routing`/`BomHeader` model — routing is unmodelled).
- `ProductionOrderHistory` (L2083) — status/audit timeline per order.
- `ProductionWastage` (L1972) — wastage with `wastageType` enum (incl. `MOULD_CHANGE`, `MACHINE_BREAKDOWN`, `POWER_FAILURE` as **reasons baked into an enum**, not a maintainable master), approve/reject workflow, `isRecyclable`/`sentForRework`.
- `MachineOeeSnapshot` (L2305) — persisted per machine/day/shift OEE (availability/performance/quality/oeePercent); written by `oee.service.ts`.
- `ProductShiftRecord` (L2370) — "best/highest" achieved qty per product per shift record (record-keeping, e.g. best-shift board).
- `ProductCapacityHistory` (L2397) — log of capacity (planned rate) changes per product/machine/shift with achievement %.
- `JobWorker` (L4267) + `DeliveryChallan`/`DeliveryChallanItem` (L4298+, shared with branch-transfer/exhibition/line-sales `ChallanKind`) — job-work-out/return register, ITC-04 support. This is the only job-work data; it lives partly outside `modules/job-work` (challans are generic documents).
- No models exist for: daily/weekly **schedule** as distinct entity (derived read-only from DailyProductionPlan — see below), **Mould/Die master**, **mould maintenance/shot count**, **machine maintenance/breakdown log**, **preventive maintenance schedule**, **downtime reason master**, **rejection reason master**, **NCR**, **in-process/final inspection**, **changeover/setup-time tracking**, **cycle-time standards per product/mould**, **energy/power meter readings**, **WIP ledger**, **capacity planning** (beyond ad-hoc `ProductCapacityHistory`).

### API modules (apps/api/src/modules/<name>)

- `machine/` — CRUD (`machine.{controller,service,validation}.ts`), permission `machines.*`.
- `machine-operation-assignment/` — CRUD + roles/employees-by-role/resolve/history-by-machine, permission `machine-assignments.*`.
- `weekly-machine-program/` (files named `weekly-program.*`) — CRUD + `/daily-planning/data` + `/pending`, permission `weekly_programs.*`.
- `daily-production-plan/` (files `daily-plan.*`, has a `.repository.ts` — the only one in this domain using a repository layer) — CRUD, permission `weekly_programs.*` (reuses the weekly-program permission key, not its own).
- `daily-schedule/` — **read-only** single `GET /` endpoint (`getDailyScheduleQuerySchema`), permission `weekly_programs.view`; confirms "daily schedule" is just a derived view over `DailyProductionPlan`, no own model/writes.
- `hourly-production/` — CRUD, permission `hourly_productions.*`.
- `product-shift-record/` — create + `findByProduct`, gated by `requireFeature("production")` only (**no granular permission key** — anyone with the production feature flag can write, not `requirePermission`).
- `production-order/` — CRUD + rich workflow: `issue-materials`, `check-materials` (STEP 2), `start-production` (STEP 5, auto-issues RM), `complete-post-production` (STEP 7→8), `/history`. Permission `production_orders.*`.
- `production-wastage/` — CRUD + `approve`/`reject`. **All six routes (create/read/update/delete/approve/reject) are gated by `requirePermission("machines.view")`**, not a wastage-specific permission — a bug: anyone who can merely view machines can create/approve/reject wastage, and the `production-wastages.*` permission keys registered in `packages/shared/src/permissions.ts` are not actually enforced here (dead permission keys on the API side; only the web `ProtectedRoute` checks them, so an API caller bypasses that gate).
- `oee/` — read-only: machine summary, production-order OEE, all-machines status. Permission `oee-dashboard.view`.
- `product-capacity-history/` — `findByProduct`, `getLatestByProductAndMachine`, `manual` change entry; gated by `requireFeature("production")` only (same gap as product-shift-record — no dedicated permission key exists in `packages/shared` for this module at all).
- `job-work/` (files `job-work.{routes,service,print}.ts`, no separate `.controller.ts`/`.validation.ts` — routes inline zod) — worker master, challans (create/receive/pdf), `/register`, `/itc04`. Permission `job-work.*`.
- `status/` — `status.service.ts` only (no routes file in this dir; mounted status page is platform/ops health, not shop-floor status) — component checks (db/migrations/worker/backups), tenant-free.
- `insights/` — `insights.service.ts` + routes: `/summary`, `/accounts`, `/ageing`, `/field-team`, `/plant` (plant/production KPIs for TV wall/companion app), `/attention`; cached 60s, permission `insights.view`.
- `dashboard/` — `dashboard.controller.ts` + `dashboard.tv.service.ts` (591 lines) — `/summary`, `/accounts-summary`, `/tv-summary`; **no `requirePermission` on any dashboard route**, only `authMiddleware` (quality issue — any authenticated user sees company-wide dashboard data regardless of role).

`machines.*`, `machine-assignments.*`, `production_orders.*`, `weekly_programs.*`, `daily-machine-planning.*`, `hourly_productions.*`, `production-wastages.*` (registered but **not enforced** by the API — see above), `goods-dispatch.*`, `shift-execution.{view,edit}`, `oee-dashboard.{view,export}`, `bill_of_materials.*`, `job-work.{view,create,manage,export}`, `production-reports.{view,export}`. No permission module registered for `product-shift-record` or `product-capacity-history` (both rely on the blunt `requireFeature("production")` flag).

### Tests (apps/api/test/integration)

Only **`jobwork.spec.ts`** and **`insights.spec.ts`** directly exercise this domain. There is **no dedicated spec** for `machine`, `machine-operation-assignment`, `weekly-machine-program`, `daily-production-plan`, `daily-schedule`, `hourly-production`, `product-shift-record`, `production-order`, `production-wastage`, or `oee` — the only coverage they get is incidental, from generic cross-cutting suites (`leak.spec.ts` tenant-isolation sweep, `tenant-codes.spec.ts` code-uniqueness sweep, `entitlements.spec.ts` feature-gate sweep). Given the size and workflow complexity of `production-order.service.ts` (multi-step state machine) and the wastage approval flow, this is a significant gap versus the repo's own "Definition of done" (happy path + every validation rejection, cross-tenant test per model).

### Notable quality issues found

1. `production-wastage.routes.ts` — every route uses `requirePermission("machines.view")` instead of the registered `production-wastages.*` keys (including `approve`/`reject`, which should probably need a stronger permission than "view machines").
2. `dashboard.routes.ts` — no `requirePermission` at all, just `authMiddleware`.
3. `product-shift-record` and `product-capacity-history` have no permission module of their own; gated only by the `production` feature flag, so RBAC can't restrict who edits capacity history/best-shift records.
4. `Machine.operatorId` is a loose `VarChar(20)`, not a FK — can't be relied on for reporting/joins; real operator assignment lives in `MachineOperationAssignment`/`MachineAssignmentOperator` instead, so the field looks like dead/legacy data.
5. `HourlyProduction.downtimeReason/rejectReason/scrapReason` and `ProductionWastage.wastageType`/`reason` are free text or a fixed enum baked into the schema — cannot be extended/renamed by a tenant admin, no analytics rollup by a stable reason code, no localisation.
6. No dedicated integration tests for this whole domain (see above).
7. `daily-schedule` module has no model of its own — it's a read view assembled from `DailyProductionPlan`; fine as a design choice but means "daily schedule" edits actually happen through the daily-plan endpoints, which could confuse anyone looking for a `daily-schedule.service.ts` write path.
8. `job-work` module has no `.controller.ts`/`.validation.ts` — all validation is inline zod in the routes file, inconsistent with every other module's `controller/service/validation` split; makes it harder to reuse the validation schemas (e.g. from a job-work-out-of-mould-repair flow) elsewhere.

## 2. Gaps — proposed features (ranked by value to a plastics SME owner/accountant/plant manager)

1. **Mould/Die master + shot-count & cavity tracking** — Without this a plastics SME cannot track tool life, plan mould changes, or bill mould amortisation to a customer's tooling cost. _Data model_: `Mould { id, mouldCode, name, cavityCount, materialCompatible[], ownerType(SELF/CUSTOMER/JOB_WORKER), customerId?, standardCycleTimeSec, ratedShotLife, currentShotCount, status(IN_USE/IN_STORE/UNDER_REPAIR/RETIRED), currentMachineId?, lastMaintenanceAt, nextMaintenanceShotCount }`, `MouldShotLog { mouldId, productionOrderId, hourlyProductionId?, shotsAdded, recordedAt }` (increment mostly derived from `HourlyProduction.qtyProduced / cavityCount`, but keep an explicit log for machines that are not cavity=1:qty). _Endpoints_: `modules/mould` CRUD + `/moulds/:id/shots`, `/moulds/:id/history`. _Screens_: Mould master list/form, "mould due for maintenance" widget. _Touches_: `machine`, `hourly-production`, `production-order`, `product` (link product→mould). Size **L** (new module + FK from Machine/ProductionOrder + shot roll-up job).
2. **Machine maintenance & breakdown log with preventive schedule** — currently `MACHINE_BREAKDOWN`/`POWER_FAILURE` are just wastage-reason enum values with no ticket, no MTTR/MTBF, no PM calendar — a core plant-manager need. _Data model_: `MaintenanceSchedule { machineId, mouldId?, type(PREVENTIVE/CALIBRATION), frequencyDays/frequencyHours/frequencyShots, lastDoneAt, nextDueAt }`, `MaintenanceTicket { id, machineId, mouldId?, reportedAt, reportedBy, breakdownStart, breakdownEnd?, category, downtimeMinutes, rootCause, actionTaken, cost, status(OPEN/IN_PROGRESS/CLOSED) }`. _Endpoints_: `modules/machine-maintenance` CRUD, `/tickets/:id/close`, `/schedules/due`. _Screens_: Maintenance calendar, ticket board, machine detail "maintenance" tab. _Touches_: `machine`, `oee` (feed MTTR/MTBF into availability), `hourly-production` (auto-suggest a ticket when downtime is logged with reason=MACHINE_BREAKDOWN). Size **L**. Sequencing: build after Mould master (shares maintenance pattern) but can ship independently for machines-only first.
3. **Downtime-reason & rejection-reason master tables** — replace the free-text/fixed-enum reasons on `HourlyProduction` and `ProductionWastage` with tenant-editable, codeable masters so owners can standardise and trend causes (top-5 downtime Pareto is a table-stakes plant report). _Data model_: `DowntimeReasonCode { companyId, code, name, category(PLANNED/UNPLANNED), isActive }`, `RejectionReasonCode { companyId, code, name, isActive }`; add nullable FK columns `downtimeReasonId`/`rejectReasonId`/`scrapReasonId` to `HourlyProduction`, keep old text columns as fallback/migration path. _Endpoints_: two small master CRUD modules. _Screens_: Settings → Reason masters; dropdown wiring in Hourly Work Report form. _Touches_: `hourly-production`, `production-wastage`, `oee` (availability/quality breakdown by reason), `insights`. Size **M**, isolated (additive columns, no breaking change).
4. **Quality control: in-process & final inspection with rejection reasons and NCR** — no inspection/hold workflow exists at all; a plastics SME serving auto/export customers needs lot-level pass/fail records and non-conformance reports. _Data model_: `InspectionRecord { id, type(IN_PROCESS/FINAL), productionOrderId, hourlyProductionId?, machineId, inspectedQty, passQty, failQty, defectBreakdown Json/relation, inspectedBy, inspectedAt, disposition(ACCEPT/REWORK/SCRAP/HOLD) }`, `NonConformanceReport { id, ncrNo, sourceType(PRODUCTION/INSPECTION/CUSTOMER_COMPLAINT), productionOrderId?, qty, defectCode, rootCause, correctiveAction, status(OPEN/CAPA_IN_PROGRESS/CLOSED), closedBy, closedAt }`, `DefectCode` master. _Endpoints_: `modules/quality-inspection`, `modules/ncr`. _Screens_: Inspection entry (shop-floor), NCR register + CAPA tracker. _Touches_: `hourly-production`, `production-wastage` (a rejection should be able to spawn an NCR), `production-order` (hold order on open NCR). Size **L**. Needs sequencing after reason-code master (#3) for shared defect codes.
5. **Changeover / setup-time tracking (SMED)** — no explicit setup/changeover event exists; `WeeklyMachineProgram.setupHours` is a plan-only estimate with nothing to compare against actuals, so setup-time reduction (a classic plastics-plant KPI) can't be measured. _Data model_: `ChangeoverEvent { id, machineId, fromProductId?, toProductId, fromMouldId?, toMouldId?, plannedMinutes, startedAt, endedAt, actualMinutes, reason(PRODUCT_CHANGE/MOULD_CHANGE/COLOR_CHANGE/MATERIAL_CHANGE), performedBy }`. _Endpoints_: `modules/changeover` CRUD + `/summary` (avg changeover time by machine/product pair). _Screens_: shop-floor "start/end changeover" button on Shift Execution Board; changeover report. _Touches_: `machine`, `weekly-machine-program`, `oee` (feeds availability loss bucket), `mould` (#1). Size **M**. Can build standalone once Mould master exists (or with a nullable mould FK before it does).
6. **Cycle-time standards & actual-vs-standard variance** — `Machine.cycleTime` is one static value per machine; there is no per-product (or per-mould) standard cycle time to compare hourly actuals against, which is the basis of the "performance" leg of OEE and of costing. _Data model_: `ProductCycleTimeStandard { productId, machineId?, mouldId?, standardCycleSec, cavityCount, effectiveFrom, approvedBy }` (supersedes ad-hoc capacity numbers currently buried in `ProductCapacityHistory`). _Endpoints_: `modules/cycle-time-standard` CRUD + `/variance?productId&machineId`. _Screens_: standards master, variance report widget on OEE dashboard. _Touches_: `product`, `machine`, `oee.service.ts` (replace its hard-coded performance calc input), `product-capacity-history` (subsume/rename). Size **M**, ideally sequenced with #1 (mould) since cycle time is mould-dependent, but can ship against machine/product only first.
7. **Downtime-driven maintenance auto-ticket + machine availability calendar** — combine gap #2 with a machine "available/blocked" calendar so weekly-program/daily-plan scheduling doesn't assign a machine that's down for PM. _Data model_: reuse `MaintenanceTicket`/`MaintenanceSchedule`; add `Machine.plannedDowntimeWindows` (or a small `MachineDowntimeWindow` table). _Endpoints_: `/machines/:id/availability?from&to`. _Screens_: Weekly program planner shows machine as blocked. _Touches_: `weekly-machine-program`, `daily-production-plan`, `machine-maintenance` (#2). Size **S** once #2 exists — sequenced, not isolated.
8. **Energy/power consumption per machine** — plastics processing is power-intensive (heaters, hydraulics); SME owners want cost-per-kg or cost-per-shift electricity tracking, and MSME/ESG reporting increasingly asks for it. _Data model_: `MachineEnergyReading { machineId, shiftId, productionDate, openingKwh, closingKwh, consumedKwh, ratePerUnit, cost }` (manual meter entry first; automated meter integration later). _Endpoints_: `modules/machine-energy` CRUD + `/report?from&to&machineId` (cost per kg produced, joining `HourlyProduction`). _Screens_: Energy entry (per shift), Energy cost report. _Touches_: `machine`, `hourly-production`, `costing` module (cost-per-unit rollup). Size **M**, isolated.
9. **Capacity planning / what-if scheduler** — today `WeeklyMachineProgram` is a flat plan with no view of total available machine-hours vs demanded machine-hours (from open `ProductionOrder`/`SalesOrder`), so a plant manager can't see overload before committing a delivery date. _Data model_: mostly a read-model/service over existing `Machine`, `WeeklyMachineProgram`, `ProductionOrder`, `ProductCycleTimeStandard` (#6) — maybe one `CapacityPlanSnapshot` table to persist a plan version for what-if comparisons. _Endpoints_: `modules/capacity-planning` `/machine-load?from&to`, `/what-if` (POST hypothetical order, get load impact). _Screens_: Capacity Gantt/heatmap by machine and week. _Touches_: `machine`, `weekly-machine-program`, `production-order`, `sales-order`. Size **L**; needs #6 for accurate hours, but can ship with rough estimates first.
10. **MRP: formal material-requirement run from the weekly/daily plan** — `ProductionOrder.requiredRawMaterialQty`/`draftRawMaterials`/`checkMaterialAvailability` exist per-order, but there is no aggregate "run MRP for the week" that nets BOM explosion against `RawMaterial.onHandQty`+open POs to produce a consolidated purchase-suggestion list — a top ask for an owner buying PP/HDPE/masterbatch in bulk. _Data model_: `MrpRun { id, weekStartDate, generatedAt }`, `MrpRequirementLine { mrpRunId, rawMaterialId, grossRequirement, onHand, onOrder, netRequirement, suggestedPoQty }`. _Endpoints_: `modules/mrp` `POST /run`, `GET /runs/:id`, `/runs/:id/create-purchase-orders`. _Screens_: MRP run result grid with "raise PO" action. _Touches_: `weekly-machine-program`, `production-order`, `bill-of-material`, `raw-material`, `purchase-order`. Size **L**; sequenced after nothing new is strictly required (BOM + RM stock already exist) but is logically the capstone of planning, so build last among planning items.
11. **WIP (work-in-progress) ledger / stage tracking** — `ProductionOrder.currentProductionStep`/`currentStepIndex` exist as loose strings with no defined `Routing`/stage master, so there's no queryable "how much is at grinding vs moulding vs packing right now" view — needed for shop-floor visibility and for costing WIP valuation at period close. _Data model_: `ProductionStage` master (per routing step), `WipMovement { productionOrderId, fromStageId?, toStageId, qty, movedAt, movedBy }`, materialised `WipBalance` view/table per order+stage. _Endpoints_: `modules/wip` `/move`, `/balance?productionOrderId`. _Screens_: WIP board (kanban by stage), WIP valuation report. _Touches_: `production-order` (replace ad-hoc step fields), `costing` (WIP valuation for balance sheet), `daily-schedule`. Size **L**; needs a `Routing`/BOM-routing model that doesn't exist yet (currently `ProductionOrder.routingId` is an unvalidated string) — sequence after a minimal Routing master.
12. **Operator productivity report** — `MachineAssignmentOperator` and `HourlyProduction.operatorId` exist but there is no report joining them into "output/reject per operator per shift", which SME plant managers use for incentive/appraisal. _Data model_: none new — pure reporting service joining existing tables (fix `operatorId` typing gap first, see quality issue #4 above — currently it's a loose string on `Machine`, but `HourlyProduction.operatorId` also appears to be a string code, should be validated against `Employee`). _Endpoints_: `insights`/`reports` addition `/reports/production/operator-productivity`. _Screens_: Operator productivity report page. _Touches_: `hourly-production`, `machine-operation-assignment`, `employee`. Size **S**, isolated, quick win.
13. **Rejection-reason & downtime Pareto / top-5 loss report** — once #3 exists, expose it as a first-class report (today OEE dashboard shows aggregate % only, not a breakdown by reason) — very commonly requested by plant managers for kaizen boards. _Endpoints_: `/reports/production/downtime-pareto`, `/reports/production/rejection-pareto`. _Screens_: Pareto chart on OEE dashboard / TV wall (`dashboard.tv.service.ts` already exists as an integration point). _Touches_: `oee`, `hourly-production`, `insights`, `dashboard`. Size **S**, sequenced after #3.
14. **Shift handover note / shift log** — no structured shift-to-shift handover (pending issues, machines running, materials short) exists; currently only implicit via `HourlyProduction`/`DailyProductionPlan` rows. _Data model_: `ShiftHandoverNote { machineId, shiftId, productionDate, outgoingBy, incomingBy, notes, openIssues Json, acknowledgedAt }`. _Endpoints_: `modules/shift-handover` CRUD. _Screens_: appended to Shift Execution Board. _Touches_: `shift`, `machine`, `daily-production-plan`. Size **S**, isolated.
15. **Job-work-out yield/wastage reconciliation report** — `job-work.receive()` already captures `returned/consumed/scrap` lines per challan, but there's no rollup report showing yield % per job worker (important since job-worker scrap directly affects a plastics SME's granule cost). _Endpoints_: extend `job-work.service.ts` with `/reports/yield?jobWorkerId&from&to`. _Screens_: Job-work yield report tab. _Touches_: `job-work` only. Size **S**, isolated, quick win.
16. **Fix `production-wastage` permission enforcement** (not a new feature, but should be bundled with any wastage work) — swap `requirePermission("machines.view")` for the already-registered `production-wastages.*` keys on all six routes, and require a stronger key (e.g. `production-wastages.approve`, currently unregistered) for `/approve` and `/reject`. Size **S**, isolated, should precede #4/#13 so approvals aren't silently over-permissioned once inspection/NCR start writing to wastage.
17. **Add `requirePermission` to `dashboard` routes and register a `dashboard.view` (or reuse `insights.view`) key** — currently any authenticated user of any role sees company summary financials/production KPIs. Size **S**, isolated.
18. **Give `product-shift-record` and `product-capacity-history` their own permission modules** instead of the blanket `requireFeature("production")`, so a tenant can, e.g., let shop-floor staff view but not edit capacity history (which currently anyone with the production feature can rewrite via `/manual`). Size **S**, isolated.
19. **Cost-per-piece / production costing bridge** — `ProductionOrder` tracks qty but the `costing` module (per CLAUDE.md) is separate; there's no explicit link from actual RM consumption (`RawMaterialTransaction` issue-type rows) + labour/energy (#8) to a per-piece standard-vs-actual cost card for a finished product batch. _Data model_: `ProductionOrderCostCard { productionOrderId, materialCost, labourCost, energyCost, overheadCost, totalCost, costPerUnit }` computed on order completion. _Endpoints_: `modules/production-order` addition `/{:id}/cost-card`. _Touches_: `production-order`, `costing`, `raw-material-transaction`, energy (#8). Size **M**; sequence after #8 for full accuracy, but material-only version can ship standalone.
20. **Integration test suite for the whole domain** — not a product feature, but given zero dedicated specs exist (see Quality issue #6), any of the above should ship with `test/integration/<module>.spec.ts` covering happy path + validation rejections + cross-tenant isolation per the repo's Definition of Done; recommend backfilling for the _existing_ modules (`machine`, `production-order`, `hourly-production`, `production-wastage`, `oee`, `weekly-machine-program`, `daily-production-plan`) as its own workstream before/alongside new gap work, so regressions in the state-machine (`production-order.service.ts`) are caught. Size **M** (backfill), isolated per module.

## 3. Sequencing notes

- **Buildable in isolation now** (no new cross-domain models needed): #3 (reason masters), #8 (energy), #12 (operator productivity report), #13 (once #3 lands), #14 (shift handover), #15 (job-work yield report), #16/#17/#18 (permission fixes), #20 (test backfill).
- **Need a shared new master first, then build on it**: #1 (Mould) is foundational for #2 (maintenance), #5 (changeover), #6 (cycle-time standards) — build Mould master first, or land those three with a nullable `mouldId` and backfill once Mould ships.
- **Need each other in sequence**: #2 depends on #1 (mould-aware) and feeds #7 (availability calendar); #6 feeds #9 (capacity planning) and #19 (costing); #4 (QC/NCR) should follow #3 (shared defect/reason codes) and can optionally consume #16's tightened wastage permissions.
- **Largest, most cross-cutting, do last**: #10 (MRP run) and #11 (WIP ledger) — both touch planning + costing + BOM/routing broadly and are best scheduled after the smaller building blocks (#1, #3, #6) land, since they consume those masters.
