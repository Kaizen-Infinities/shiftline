# P2-09 — Leave management

## Shipped

- `LeaveRequest` model (audited, RLS), migration `20260914090000_leave_management`: employee,
  leave type, from/to dates, half-day flags at either end, `days`, reason, status (PENDING,
  APPROVED, REJECTED, CANCELLED), approver, decided-at, comments, cancelled-at. Same migration
  adds `LeaveType.allowNegative` (leave without pay) and a seeded `LWP` leave type in
  `labourService`'s default set.
- `apps/api/src/modules/leave/` — `leave.calc.ts` (pure: the financial-year code for a date, and
  the days a request costs once weekly-offs and holidays are taken out), `leave.service.ts`,
  `leave.validation.ts`, `leave.routes.ts` under `/api/leave`. Approval and cancellation move
  `LeaveBalance.taken` the same field `labourService.takeLeave` moves, so the ledger looks the
  same whichever path touched it; rejection and a merely-pending cancel never touch it.
  Overlapping PENDING/APPROVED requests are refused, and a request beyond the balance is refused
  unless the leave type's `allowNegative` is set.
- `src/jobs/leave.job.ts`, queue `payroll.leave.accrual`, scheduled 02:00 IST on the 1st (before
  the depreciation run): for every active tenant and active employee, totals attendance
  (`PRESENT`/`HALF_DAY`/`LEAVE_PAID`) from the start of the financial year through the month just
  closed and calls `labourService.accrue` with that cumulative total — idempotent because the
  total does not change on a second run for the same month and `accrue` already overwrites rather
  than adds.
- Routes: `GET/POST /api/leave/requests`, `POST .../:id/{approve,reject,cancel}`,
  `GET /api/leave/calendar?month=`, `GET /api/leave/me` (200 with `linked:false` instead of a
  404 when the calling user has no employee record — same shape as the existing employee "my
  profile" endpoint). Permissions `leave.view`, `leave.request`, `leave.approve`, registered in
  `packages/shared`, feature `payroll`; `leave.request`/`leave.view` are on every role that maps
  to an employee (STORES, PRODUCTION, SALES_EXEC), `leave.approve` on ACCOUNTS (and OWNER, which
  gets everything), `leave.view` alone on AUDITOR.
- Notifications through the existing `notify` helper: whoever holds `leave.approve` on a new
  request, the requester's linked user on a decision.
- Web: `/hr/leave` (requests with filters, inline approve/reject/cancel, a month calendar) and
  `/me/leave` (self-service balances, a request form, own requests with cancel), both under the
  Payroll sidebar section, in `e2e/smoke.spec.ts`.
- `apps/api/test/integration/leave.spec.ts` — 11 integration tests: computed days excluding
  holidays/weekly-offs, overlap refusal, insufficient-balance refusal, an `allowNegative` type
  going negative, approve/reject/cancel against the ledger, the calendar, `/me` linked and
  unlinked, the accrual job's idempotency, a permission refusal for both request and approve, and
  a cross-tenant check. `labour-code.spec.ts` and the rest of the payroll suite still pass
  unmodified.

## Decisions worth knowing

- **The ledger stays one thing.** A request never gets its own balance; approving and cancelling
  both move `LeaveBalance.taken`, the same field the hand-entry path in `labour.service.ts`
  already moves. That keeps a balance explainable regardless of which path touched it, at the
  cost of the two paths needing to agree on the fyCode a date falls in (April–March, computed
  from `fromDate`).
- **Cancelling an approved request never deletes it.** It flips to CANCELLED with a
  `cancelledAt`, and the ledger gets a reversing move rather than the row disappearing — the
  calendar and the audit trail both keep the history of what happened and when it was undone.
- **The accrual job recomputes the cumulative total rather than adding a delta.** The spec reads
  as "call `accrue` once per employee per month with last month's days worked," but `accrue`
  itself sets `LeaveBalance.accrued` to an absolute figure, not an increment — so the job totals
  attendance from the start of the financial year through the month just closed, every run. That
  makes a second run for the same month land on the same balance without any separate
  "already ran" tracking, at the cost of re-scanning attendance back to April every month; for a
  company's employee count and a one-year attendance window that is cheap, but it is worth
  knowing if a tenant carries years of dense attendance history.
- **Weekly-offs come from `PayrollConfig.weeklyOffDays`, not from the `Shift` model.** `Shift`
  has no day-of-week field; the tenant's payroll config already carries the list every other
  attendance calculation uses, so leave reuses it rather than adding a second source of truth.
- **The calendar groups by department, not business place.** `Employee` carries a `departmentId`
  but no business-place relation in the current schema; adding one was out of scope for this
  package.

## Half-done / known gaps

- No comp-off, no change to leave encashment, no actuarial anything — all explicitly out of
  scope per the spec, unchanged from P1-17b.
- The HR request form on `/hr/leave` takes a raw employee id rather than a searchable picker; the
  self-service form on `/me/leave` does not need one since it always uses the caller's own
  linked employee. A proper employee picker on the HR screen is a small follow-up once there is
  an employee-search endpoint that does not require `payroll.view`.
- The calendar endpoint returns a flat list of approved absences for the month rather than a
  day-by-day grid; the web screen renders it as a table. A calendar grid view is cosmetic and can
  be built from the same data without a backend change.
- `leaveType.allowNegative` only ships on the seeded `LWP` type; there is no screen to flip it on
  an existing type yet (it is set through `POST /api/labour/leave-types`, which already accepts
  the field, just with no button in front of it on `LabourEntitlementsPage`).
