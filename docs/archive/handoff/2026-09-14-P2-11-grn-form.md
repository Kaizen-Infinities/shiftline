# P2-11 — GRN invoice form: TDS toggle, currency and cheque fields

## Shipped

- **TDS toggle on the create form** (`InvoiceDetailPage.tsx`): a "Deduct TDS on this bill"
  checkbox, a section picker fetched from `/api/tds/sections` (gated behind `tds.view` — the
  section fetches and the whole panel are skipped for a role without it), and a live preview
  line calling `/api/tds/preview` with the selected supplier's own `pan`/`deducteeType`/
  `higherRate206AB` (the same values the server itself would resolve, so the preview matches
  what accepting it will actually deduct). The preview shows rate, TDS amount and net payable,
  or the "below threshold" reason when the section's threshold isn't crossed yet. The Order
  Summary panel gets matching "Less: TDS" / "Net Payable" lines when a deduction is active.
- **Supplier default section** (`Supplier.defaultTdsSectionCode`, migration
  `20260914110000_grn_form`, additive column): when the selected supplier carries one, the
  section picker defaults to it — the person can still pick a different section, which wins.
  Wired through `supplier.validation.ts` (both create and update; the service already spreads
  validated fields straight into the Prisma call, so no other backend change was needed) and
  covered by a new test in `tds-documents.spec.ts` that round-trips it through
  `POST`/`GET`/`PUT /api/suppliers`.
- **Currency fields on the create form**: a currency picker (default INR; the exchange-rate and
  foreign-total fields stay hidden for INR), the exchange rate defaulted from
  `currencyService.rates()` (the rate on or before the GRN date, the same rule the currency
  screen documents) and left editable, and a Foreign Total line next to the GRN Details grid and
  again in the Order Summary once items are priced.
- **The Payments section itself.** The form already carried `payments` state, a `newPayment`
  draft and `handleAddPayment`/`handleRemovePayment` handlers from an earlier pass, but no JSX
  ever rendered them — payments could only ever arrive already-saved from an existing GRN, never
  be added from this screen. This package builds the missing section: a table of payments already
  on the bill/being added, and an add-payment row with amount, an Instrument select (Cash / Bank
  Transfer / Cheque), reference number for non-cash, payment date, and — only for Cheque — cheque
  number, cheque date, bank and drawer, with a "Post-dated" note when the cheque date is after
  the payment date (mirroring `isPostDatedCheque` in `voucherPosting.service.ts`). Client-side
  validation matches the zod schema exactly: cheque number required and ≤20 chars, bank ≤120,
  drawer ≤160, reference required for any non-cash method, payment date required and not in the
  future.
- **View page** (`GrnInvoiceViewPage.tsx`): a no-print summary panel under the action buttons
  showing the currency conversion (`USD 1,234.56 @ ₹83.10 = ₹…`) when the bill isn't in INR, the
  TDS deduction (`TDS 194C — ₹1,000 deducted, net payable ₹49,000`) with a link to
  `/compliance/tds`, and each payment with its instrument, a POST-DATED badge, and — for a
  cheque — its register status (`IN_HAND`/`DEPOSITED`/`CLEARED`/`BOUNCED`) fetched from
  `bankingService.cheques()` and matched by `sourceDocId` back to this GRN (the endpoint has no
  document filter, so the match happens client-side). The printable card itself also gets a
  Currency row in its meta block.

## Decisions worth knowing

- **TDS and currency stay locked after creation, matching the rest of the form.** The update
  endpoint (`grn-invoice.service.ts`'s `updateGrnInvoice`) never processed `deductTds`/
  `tdsSectionCode` even before this package — `UpdateGrnInvoiceSchema` accepts the fields but the
  service silently drops them — and almost every other field (items, dates, discount, rounding)
  is already `disabled={isEditMode}` in this form; editing an existing GRN here really only means
  adding a payment against it. The TDS toggle and currency fields follow that same lock rather
  than exercising a code path the backend doesn't implement; changing that is a real feature
  (re-running or amending an already-posted TDS deduction) and out of this package's size.
- **The supplier default is a suggestion, not a lock.** `tdsSectionTouched` tracks whether the
  person picked a section by hand; the default-from-supplier effect only fires while that's
  false, so switching suppliers after manually picking a section does not clobber the choice.
- **Cheque register status on the view page is matched by `sourceDocId`, not stored on the
  payment.** `GET /api/banking/cheques` has no document filter, so the client fetches issued
  cheques and filters by `sourceDocId === selectedItem.id` (the column P2-06 added precisely so
  the deferred-clearing path could find its way back to the parent document); the payment's own
  `chequeNo` then matches the specific row for that instrument.
- **The `tdsService.preview` and `currencyService.rates` web helpers were missing, not just
  unused.** `tdsService.ts` had every other TDS endpoint wired except `/api/tds/preview`
  (present in `API_PATHS` since P1-15/P2-05 but never called); it's added here. The rate lookup
  reuses the existing `currencyService.rates()` from `advanceService.ts` (P1-14's currency
  screen) rather than adding a new endpoint — picking the latest rate on or before the invoice
  date client-side mirrors what `currencyService.rateFor()` already does server-side.

## Half-done / known gaps

- No screen sets `Supplier.defaultTdsSectionCode` yet — the column, validation and API round trip
  are done, but `SupplierForm.tsx` doesn't offer a field for it (the same way `higherRate206AB`
  and `deducteeType` also aren't editable from that screen today). Until then it can only be set
  by a caller that sends the field directly, same as those two.
- The expense and sales-invoice forms are P2-12's; this package only touched the GRN invoice
  screens and did not add or edit `e2e/smoke.spec.ts` (no new route, no sidebar entry, no heading
  changed on either screen).
- Sales invoices still have no manual receipt-recording endpoint (a P2-06 gap, unchanged here),
  so there was nothing to build a Payments section for on that document even if it were in scope.
- The cheque register match on the view page assumes `chequeNo` is unique per bill; two cheque
  payments on the same GRN with the same (re-typed) cheque number would both match the first
  register row found. Narrow in practice — cheque numbers are bank-assigned and distinct.

## Next

## Changelog sentence

The GRN invoice form now offers to deduct TDS with a live preview before you accept it, prices a
bill in a foreign currency with the day's rate, and records a cash, bank or cheque payment
(post-dated cheques flagged) — all three, along with the cheque's register status, now show on
the invoice's view page too.
